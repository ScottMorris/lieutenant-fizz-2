# Platform skeleton

Milestone 0 built the platform skeleton: a fixed 60 Hz loop that runs on Web and DOS from the same Rust rules and hashes the state so a script can prove that native x86_64, Web (WASM) and DOS (headless DOSBox) agree. Milestone 1 replaced the skeleton's throwaway marker rules with the first playable slice, and the slice is now the product the gates compare. Milestone 0's marker crate, `fizz-hello`, is deleted; its numbers are kept below as history. This document describes the layers as built, the decisions behind them, how to run each check and what has not been verified. [`ARCHITECTURE.md`](ARCHITECTURE.md) holds the layer plan and the parity policy this skeleton implements.

`InputFrame` carries `held` and `pressed` button sets. `InputLatch` turns key transitions into frames, and the rules act on `held | pressed`, so a tap shorter than one tick still counts. `Buttons` are `UP=1`, `DOWN=2`, `LEFT=4`, `RIGHT=8`, `JUMP=16`, `POGO=32` and `FIRE=64`.

The rules are `fizz-ep2`, built on `fizz-phys`. Milestone 0's `fizz-hello` was a marker with a position, a velocity, a heading from `atan2` of the held direction, and a dash count; the trigonometry was deliberate, to make the x87 precision setting an observable part of the hash. It ran a 600-tick script (`M0_SCRIPT`) whose transcript, header `M0 REPLAY 1`, ended `FINAL TICK 600 HASH efc699079baa6a88` on native, Web and DOS. Nothing compares that hash any more.

The DOS workspace is separate from the root workspace. It uses a custom target (`dos/dos-elf.json`), `-Zbuild-std` and `RUSTC_BOOTSTRAP=1`, so host checks never need `rust-src` or the nightly-only flags.

## The hash transcript

A replay runs the slice's built-in 1,757-tick script (`SLICE_SCRIPT`) from the start of the level and prints a transcript. Version 1 is plain text, one record per line:

```text
SLICE REPLAY 1
TICK 0 HASH <hex16>
TICK 60 HASH <hex16>
...
FINAL TICK 1757 HASH <hex16>
```

`TICK` lines appear at tick 0 and after every 60 ticks. `EVENT <tick> <name> <fields>` lines, which record the semantic events the rules emitted during a tick, come before the `TICK` or `FINAL` line of that tick (the slice has thirteen kinds, from `EVENT <tick> cluck <variant> <chicken>` to `EVENT <tick> jump <x> <y>`; see [Events and clucks](#events-and-clucks)). The parity gate compares the lines that start with `TICK `, `FINAL ` or `EVENT `, and requires the golden's first line, the header, from every platform. Platforms may add lines with other prefixes: DOS prints `EXIT yes`, `FPU CW 027F`, `BIOS TICKS <n>`, `VECTORS RESTORED yes` and `SIZE`, and the `/BENCH` and `/PROBE` modes print `BENCH ...` and `PROBE ...` lines. Those are checked by `tools/check-dos.sh`, not by the parity gate.

The version in the header changes only when an existing line changes shape. Adding the cluck's `EVENT` lines, later the chicken's index to them, then the `shotend` lines and then the sound and caption events did not bump it, because no consumer read the old form, and the golden was regenerated each time.

The golden file is `crates/fizz-ep2/slice-replay.txt`. All three platforms produce it: native x86_64 (`cargo run -p fizz-ep2 --example replay`, which calls `fizz_ep2::replay`), Web (WASM through `wasm-bindgen`, run under Node or Bun by `tools/web-replay.mjs`) and DOS (`FIZZ2.EXE /REPLAY` in headless DOSBox with the x87 at 53 bits, collected in an 8,192-byte buffer). `tools/check-parity.sh` compares native, Web and DOS with it and prints `PARITY ok <hash>` with the hash read from the golden's `FINAL` line; `tools/check-dos.sh` makes the same comparison for DOS alone, and the host tests of `fizz-present-web` compare the Web transcript with it.

### History: the Milestone 0 transcript

Milestone 0's replay ran 600 ticks of `fizz-hello` with the header `M0 REPLAY 1` and hashed the tick, then `x`, `y`, `vx`, `vy` and `heading` as `f64` bits, then `dashes` as a `u32`. All three platforms ended `FINAL TICK 600 HASH efc699079baa6a88`, and its `BIOS TICKS` bound was 180 to 184. The crate, its golden `m0-replay.txt` and that gate were deleted when the slice became the gated product; the progress archive keeps the transcript in `tools/progress-report/snapshots/m0.json`.

### The slice transcript

The slice replay (`fizz_ep2::replay`, golden `crates/fizz-ep2/slice-replay.txt`) has the header `SLICE REPLAY 1`: a `TICK` line at tick 0 and after every 60 ticks, then `FINAL TICK 1757 HASH <hex16>`, with `EVENT` lines between them (see [Events and clucks](#events-and-clucks)). It takes an `InputFrame` stream through `fizz_ep2::step` and `fizz_ep2::hash`. Native prints it with `cargo run -p fizz-ep2 --example replay`, DOS runs it as `FIZZ2.EXE /REPLAY`, and the Web runs it through `tools/web-replay.mjs`; `tools/check-parity.sh` and `tools/check-dos.sh` compare each with the golden file.

The slice hash covers, in this order, with floating-point fields as `f64` bits and counts as `u32`:

1. the tick (`u64`);
2. Ben: `x`, `y`, `vx`, `vy`, `face`, `squash`, `dead`, `inv`, `shoot_t`, then a flags byte (bit 0 pogo, bit 1 cut, bit 2 on the ground, bit 3 bumped), then `look_up`, `look_down` and `look_offset` as `f64` bits and `aim` as one byte (`-1`, `0` or `1`, as an `i8` cast to `u8`);
3. the `WorldFlags` word (bit 0 red key carried, bit 1 red door open, bit 2 exit reached, bit 3 blue key carried, bit 4 blue door open), `ammo` and `deaths`;
4. `map.switches`, which holds the doors (a closed door is a set bit: channel 1 the red door, channel 2 the blue one);
5. the chicken count, then per chicken `x`, `y`, `vx`, `vy`, `dir`, `stun`, a flags byte (bit 0 on the ground, bit 1 touching Ben, bit 2 dead), the cluck timer (`u32`) and the cluck stream's draw count (`u32`);
6. the shot count, then per shot `x`, `y`, `vx`, `vy` and `life`;
7. the snack count, then one byte per snack in the order the level adds them: 1 if Ben has taken it, 0 if not. The soda cans are in this list, after the snacks, so a taken can is hashed like a taken snack (the five shots it gave are in `ammo`, field 3). A snack's or a can's kind and position are level data and are not hashed, and nor is the score, which is worked out from the snacks taken (a can is worth none). The blue key and door need no field of their own: they live in the flags word and in `map.switches`.

The hash is a 64-bit FNV-1a (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`) over the bytes of these fields, integers as little-endian bytes and each `f64` as its IEEE 754 bit pattern, so a difference of one unit in the last place changes the digest. `StateHash` in `fizz-sim` implements it and `hash` in `crates/fizz-ep2/src/world.rs` fixes the order. The transcript prints the digest as 16 lower-case hexadecimal digits.

The golden hash today is `a08501a57d509e8a` (`FINAL TICK 1757`), and the golden's tick 0 line is `TICK 0 HASH 7029932ff06fa35d`. The golden changes whenever a hashed field is added. Milestone 0's marker ended `efc699079baa6a88` and is gone. The first slice script ended `d1a225bf14ab4828`, the chicken's cluck timer and draw count made it `2145503c0d3b625f`, the look timers, look offset and aim made it `0edebb797e63edff`, the playground (the snacks' taken flags, the blue key and door, and a script that grew from 1,268 ticks to 1,681) made it `e3d629fda94149ab`, and the soda cans (two more entries in the snack list, and a script that grew to 1,757 ticks so Ben picks one up and fires again) made it `a08501a57d509e8a`. A hash that changes with no field added is a bug until proven otherwise.

The look timers, the look offset and the aim are hashed because earlier input shapes them and later pictures and poses depend on them. The camera position itself and the event list are not hashed: the camera is a function of Ben's state (see [Looking up and down](#looking-up-and-down)). Tests in `crates/fizz-ep2/src/world.rs` lock the order three ways: an independent byte-by-byte FNV-1a over a hand-built sequence, a pinned digest of a world with every field set, and a check that changing any one field changes the digest.

## Numeric model decisions

The model is Fizz 1's, described in [`ARCHITECTURE.md`](ARCHITECTURE.md). The skeleton settled these specifics:

- State is `f64` and the rules use basic IEEE operations. `fsin` and `fsqrt` are never used.
- `libm` is pinned at `=0.2.16` with `default-features = false`. On x86 targets without SSE, its `exp`, `exp2` and `exp10` always run x87 assembly, so the exp family is banned in rules crates.
- Velocities with a magnitude below 2^-1000 (about 9.3e-302) snap to zero at the end of Ben's move (`SNAP` in `crates/fizz-ep2/src/ben.rs`). Without it, an idle pogo's horizontal drag decays for ever and reaches subnormal values, where x87 at 53 bits and SSE2 round differently. Milestone 0's marker used a threshold of 1/1024 and the slice's is far smaller. A unit test runs an idle pogo for 30,000 ticks and checks that every velocity is zero or at least the threshold, and another pins the threshold. It is a departure from Fizz 1, listed under Departures below, and no golden trace changes with it.
- The x87 control word is `0x027F` (53-bit precision, all exceptions masked). The program sets it before the first tick. The runtime's `_start` only runs `FNINIT`, which leaves `0x037F` (64-bit precision), so a program that skips the step would hash differently.
- Interrupt handlers never touch the x87.

## Ben against Fizz 1

`fizz-ep2` holds Ben's movement, ported line for line from Fizz 1's `tick_ben_move` (with the alive and dead branches of `tick_ben`, `tick_head_bump` and `fire`) on top of `fizz-phys`; the rest of Fizz 1's `World::step` for the slice lives in `crates/fizz-ep2/src/world.rs`. It is proved against golden traces that Fizz 1's own simulation wrote, committed in `crates/fizz-ep2/tests/fizz1/`: `crates/fizz-ep2/tests/fizz1_traces.rs` parses each shared `.scn` scenario, runs it and compares every tick with the `.trace` as `f64` bit patterns, with no tolerance. The traces are regenerated with `tools/fizz1-trace`, which needs Fizz 1 at its pinned commit; the test needs only the committed files.

The traces are `FIZZ1 TRACE 2` files: format 2 adds `look_up`, `look_down` and `aim` columns after `switches`, and the sixteen older traces were regenerated with their old columns byte for byte unchanged. Floating-point values are written as 16 hexadecimal digits of their bit pattern. Each trace names the Fizz 1 commit it came from (`4bce036`). `tools/fizz1-trace` also checks that no scenario triggers an automatic mantle. `cd tools/fizz1-trace && cargo run --release -- --check --all` (with `FIZZ1` at that commit) fails if a committed trace differs from what Fizz 1 writes today.

Proven bit for bit, all eighteen scenarios:

| Scenario | What it proves |
| --- | --- |
| `fall`, `run`, `jump_full`, `jump_cut` | gravity and terminal speed, walking and friction, the jump and its cut |
| `pogo_idle`, `pogo_held`, `pogo_ceiling` | the pogo and its held high bounce, the squash (slightly negative, never clamped), the taller head box |
| `oneway`, `wall_step`, `slope` | one-way platforms, the wall stop, the 0.55 step-up, slopes |
| `gloop_patrol` | the chicken's patrol, turning at a wall and at a ledge |
| `stomp`, `stomp_pogo` | landing on the chicken: 3 s stun, bounce 12 (20 with the pogo), repeated bounces while it stays stunned |
| `fizz_stun` | a shot stuns the chicken for 6 s, and a second shot passes through the stunned one; ammo and the shot's flight |
| `key_door` | picking up the red key and opening the red door by walking into it |
| `look` | the look timers: Up or Down held alone while idle counts up and resets on release; no look while both are held, while running, in the air or on the pogo |
| `aim` | the aim and the shot: level, Up on the ground (straight up from the middle of the body), Down on the ground (still level), Down in the air (straight down from the feet) |
| `route` | a run through a small maze that ends on spikes: one-way ledges, jumps and the spike death |

The harness runs every scenario through the whole `World` and compares every field a trace carries, Ben's (including `look_up`, `look_down` and `aim`; trace format 2 adds those three columns after `switches`) and the first Gloop's. One bit is masked in the `switches` field: Fizz 1 rewrites the red door's tile when it opens and never touches its switch word, while Fizz 2 keeps the door as a switched tile on channel 1 (a closed door is a set bit), so the door's bit is left out of that comparison. The facts the traces do not show (the door staying shut without the key, what a death keeps and drops) are covered by unit tests in `crates/fizz-ep2/src/replay.rs`.

The slice level is `crates/fizz-ep2/src/level.rs`: 32 by 48 tiles, written as text and baked at compile time, with the tile alphabet documented in the module. The replay proves it can be finished with the real physics: the script reaches the exit in 1,757 ticks with both doors open and both keys spent, after one death on the spikes carrying the red key (the key drops and lies where it began; the world respawns Ben, resets the chicken and the ammo). It shoots the chicken in the first life and stomps it in the second. The last part of the second life is the playground on the gallery (see [The snack nook](#the-snack-nook)).

### The snack nook

The gallery at the top of the right shaft holds the slice's playground, small set pieces that make each of the new events happen in play and in the parity replay. It is level data in `crates/fizz-ep2/src/level.rs`; the rules are Fizz 1's. The exit is behind the blue door, under a lintel of blocks that runs to the top of the map, and the right of the gallery is a wall, so the way to the exit goes through the nook:

| Set piece | What Ben does | What fires |
| --- | --- | --- |
| Five shots against the right wall | Fire five times (Ben carries five), then once more | `fire` five times, `shotend` five times, then `dud` |
| A soda can on the floor by the right wall, three tiles from where Ben stands | Walk into it, then fire five more shots at the wall | `can` (five shots, Fizz 1's `fsssht`), then `fire` and `shotend` five times again |
| Two cheezies hanging under the shelf | Jump under the shelf: the cheezie is picked up and the head meets the shelf | `snack`, `headbump` (and `jump`) |
| The shelf, four tiles up | Take the pogo (the pogo key toggles it), bounce low twice, then hold Jump for the high bounce and drift left onto the shelf | `bounce` at every landing, `headbump` where the pogo's taller head meets the shelf |
| A soda can at the right end of the shelf, then a cheezie, a chocolate and a cookie, then the blue key | Land on the shelf and bounce along it to its left end | `can` as Ben lands, `snack` three times (1, 2 and 5 points), then `key` with colour 1 |
| The blue door | Drop off the shelf's left end facing the door with the blue key | `dooropen`; the lintel's head bump and more bounces follow on the way to the exit |

Pickup rules and points are Fizz 1's `tick_ben_contacts`: an item is taken when Ben's body overlaps a 0.8 tile box around its centre; a cheezie is worth 1 point, a chocolate 2 and a cookie 5 (`World::score`). Fizz 1's USB stick, green door and extra lives are not in the slice. The soda can is Fizz 1's `ItemKind::Soda` (`ammo += 5`, caption `fsssht`): a `SnackKind::Soda` entry in the same list (`World::snacks`), taken by the same overlap test, worth no points, and giving `SODA_AMMO` (5) more shots with no cap, as Fizz 1 has none. It raises `Event::Can` instead of `Event::Snack`. The cans are the last two entries of `level::SNACKS`, so the snacks keep their places in the hash order. Before the cans the hash was `e3d629fda94149ab` over 1,681 ticks; with them it is `a08501a57d509e8a` over 1,757. A death puts the snacks and the cans back, and the ammo at five (Fizz 1 reloads the level and the items with it, but it keeps the ammo across a death, as its `Game` is not reset by `load_level`; the slice has always started the blaster over at five, see the respawn rules below), and keeps an open blue door, as it keeps the red one. The score is drawn by the HUD (see [The DOS HUD](#the-dos-hud)); it is worked out from the snacks taken by `fizz_slice_view::hud`, so it is not hashed.

### Events and clucks

`World::events()` returns the `Event`s the last `World::step` emitted, in the order they happened; the next step clears them, and every one happened on `World::tick`. There are fifteen. `Event::Cluck { variant, chicken }` has `variant` below `CLUCK_VARIANTS` (4) and `chicken` the chicken's index in `World::chickens`. `Event::ShotEnd { x, y }` is emitted once for each of Ben's shots that ends (it hit a wall or the map's edge, its life ran out, or it stunned a chicken, which are Fizz 1's `gone` cases; a respawn that clears the shots emits nothing), with the shot's position in sixteenths of a tile, which are the slice's logical pixels, rounded down, y up. The slice has no enemy shots, so the event has no owner. The other thirteen are the moments Fizz 1 raises a caption or a sound, each with `x` and `y` in sixteenths of a tile (y up, rounded down) at the point Fizz 1 puts the caption: `Fire` ("fzzt", at the new shot, half a tile up), `Dud` (fire with no ammo, "click, no fizz"), `Stomp { chicken }` ("bonk", above the chicken), `Stun { chicken }` (a shot stuns an unstunned chicken, "fizzled"; the shot also ends, so a `ShotEnd` follows it, and a wall or timeout is a plain `ShotEnd`), `Death` ("whoa!"), `Key { colour }` (0 red, 1 blue, 2 green; the slice has the red and the blue one), `DoorOpen` ("clunk"), `Exit` ("ta-da!"), `Bounce` (the pogo, "boing"), `HeadBump` ("clunk", once per rise), `Jump` (sound only, no caption), `Snack` (Fizz 1's "crunch", half a tile above the snack's centre) and `Can` (Fizz 1's "fsssht" for a soda can, at the same point). Ben does not raise events himself: `Ben::tick` returns a `BenFlags` value (jumped, bounced, bumped, fired, dud, each with its point) and `World` turns it into events, so Ben's movement is unchanged. Within a tick the order is Ben's own (bounce or jump, fire or dud, head bump), then his contacts (exit, door, death, key, stomp), then clucks in chicken order, then shots from the last shot to the first (a stun, then its shot end). Events are output only and are not hashed, so adding the first thirteen changed the golden's `EVENT` lines and not a single `TICK` or `FINAL` line. `Snack` came with the playground, and `Can` with the soda cans, which moved the hashes on purpose; `every_tick_and_final_line_is_pinned_apart_from_the_events` pins the non-`EVENT` lines of the new golden. The rules never touch audio: a presenter plays the events. A presenter that runs several steps between frames reads the list after each step.

Each chicken has a cluck timer and its own stream of random numbers: Fizz 1's `fizz_phys::rng::hashf` over the world tick, the chicken's index and the number of draws the chicken has made, with a fixed salt. It is a pure function of integers, so there is no platform random source; the only floating-point work is `hashf`'s own division by 2^32, a multiply by a small integer and a truncation, all exact or correctly rounded in IEEE 754 and so the same on native, Web and DOS. The chicken's walk draws nothing, which is why Fizz 1's traces, which compare only Fizz 1's fields, stay bit for bit identical. The first draw at spawn (or respawn) sets the timer, uniform over 90 to 360 ticks (1.5 to 6 s). The timer counts down one per tick while the chicken is alive and not stunned; at zero the next draw is the variant and the one after is the next timer, and the world emits `Cluck`. Stunned chickens do not cluck and their timer holds still while they are stunned, so a stun delays the next cluck by its length and the chicken never clucks while stunned or the instant it wakes; a dead chicken (which Fizz 1 never produces) does not cluck either. The timer and the draw count are in the hash, so a platform whose stream drifts shows up in the parity gate.

The transcript prints `EVENT <tick> cluck <variant> <chicken>` for each cluck and one line per other event (integers only): `shotend <x> <y>`, `fire <x> <y>`, `dud <x> <y>`, `stomp <chicken> <x> <y>`, `stun <chicken> <x> <y>`, `death <x> <y>`, `key <colour> <x> <y>`, `dooropen <x> <y>`, `exit <x> <y>`, `bounce <x> <y>`, `headbump <x> <y>`, `jump <x> <y>`, `snack <x> <y>` and `can <x> <y>`, in the order of `World::events()`, before the `TICK` or `FINAL` line of the same tick: the line reads as what happened during that tick, and the hash after it as the state the tick left. The header stays `SLICE REPLAY 1` because no existing line changed shape. `fizz_ep2::replay::{write_start, write_step, write_final}` write the pieces, so the DOS build, which paces the script itself, prints the same bytes `replay` does. The slice replay has five clucks, at ticks 197 (variant 2), 853 (variant 1), 1094 (variant 0), 1382 (variant 3) and 1720 (variant 0), and thirteen shot ends: `EVENT 96 shotend 37 337` (a shot fired straight up), `EVENT 106 shotend 243 45` (a shot into the wall), `EVENT 281 shotend 64 189` (the shot that stuns the chicken) and the ten shots Ben spends on the gallery wall (five, then five more after the `can` at tick 1190 refills the blaster; a second `can`, at tick 1522, is on the shelf). It ends `FINAL TICK 1757 HASH a08501a57d509e8a`. Counting every kind, the 83 `EVENT` lines are 22 `jump`, 13 `fire`, 13 `shotend`, 9 `bounce`, 5 `snack`, 5 `cluck`, 4 `headbump`, 3 `key`, 2 `dooropen`, 2 `can` and one each of `dud`, `death`, `exit`, `stomp` and `stun`: the script fires every kind of event the slice has. The transcript is 3,004 bytes against the DOS buffer's 8,192. `tools/check-dos.sh` and `tools/check-web-slice.sh` compare `TICK`, `FINAL` and `EVENT` lines with the golden file, so the number, tick, variant and chicken of every cluck, and the tick and position of every shot end, match on native, Web and DOS.

Event captions (`crates/fizz-slice-view/src/captions.rs`) are presentation state kept beside `Puffs`, not on the world. The effect ids (`EFFECT_*`, `EFFECT_COUNT`), the shared caption ids (`CAP_*`) and the caption styles live in `fizz_ep2::cues`, because a baked rule refers to them by number and they are in the pack's compatibility number; the presenter re-exports the numbers and keeps the words, colours and placement. `presentation(&Event)` is a pure table giving each event its sound effect id (cluck 0 to 3, fzzt 4, stun 5, bonk 6, hurt 7, win 8, key 9, clunk 10, plink 11, boing 12, jump 13, crunch 14, soda 17, door 19; ids 15, 16 and 18 are alternates no event plays) and its caption, if any (`EVENT_CAPTIONS`: text and Fizz 1's colour, with a dark colour for the DOS fade). `EventCaptions` is a fixed list of 6 slots with no allocation, fed by `observe(world, w, h, options)` after every step, the way `Puffs` is, and read back with `views(..)`. It follows Fizz 1's rules: the same caption (the word is the id, so a door and a head bump are both "clunk") within 11 ticks (Fizz 1's 180 ms is 10.8 at 60 ticks) is dropped, and a dropped caption does not renew the window; a caption is dropped when its point is more than `CAPTION_REACH` (16 pixels) outside the picture, which is Fizz 1's 50 CSS pixels as 5% of a roughly 1000 pixel viewport, scaled to 320 pixels, and the cluck caption already used; the test is made once, when the caption is raised, against that tick's camera, and the word then stays at its map position while the camera moves; a full list replaces slot 0 as Fizz 1's DOS port does, after first taking any slot whose caption is over; there is no priority. Life is 57 ticks and the rise 12 pixels on both platforms: Fizz 1's Web text is 950 ms and its DOS port 45 ticks, and the two here must match, so the Web value (the cluck caption's) is used. The list is fed whether or not Captions is on; the setting only gates drawing. The word is centred on the event point. DOS draws it with `pfont` in `draw_slice_captions`, after the chicken captions and clipped by the frame (`fizz_present_dos::ViewFx` bundles `Puffs` and `EventCaptions` for the loop and the bench); the Web `App` appends the views to its live captions, `caption_anchor_above(i)` says whether the word rests 32 view pixels above its y (a chicken's feet) or on it (an event point), and `main.js` shows both as text through the same `caption_*` accessors. Nothing here is hashed and the rules never read it. The same table feeds the sound: `event_sound(world, event, w, h, options)` returns the effect id and the `Placement` of the event's point against the camera (a cluck's from its chicken), and both presenters play that, whatever the Captions setting says; Fizz 1's 180 ms dedupe is for the words only and is not applied to sound. `EventCaptions::show_six` fills the list for `/BENCH` and screenshots.

Each chicken also carries two pieces of presentation state, `cluck_age` and `cluck_variant`. `World::step` adds one to every chicken's `cluck_age` (saturating) at the start of its turn and, when the chicken clucks, sets `cluck_age` to 0 and `cluck_variant` to the cluck's variant; `cluck_age` is `CLUCK_NEVER` (`u32::MAX`) until the first cluck, and a respawn resets both. They are not part of the state hash and no rule reads them: they only tell a presenter how far into a cluck a chicken is, so it can draw an open beak and a floating caption from the world and the tick alone. The DOS presenter draws the caption as pixel text into the picture, as written (mixed case, `buh-GAWK!`), in Fizz 1's proportional pixel font (`fizz_view::pfont`, data exported to `fizz_font_data.rs`), centred on the chicken by the word's measured width. The Web presenter does not: its picture never holds captions, because the page scales the canvas several times and an 8 by 8 glyph would stand tall. `App::render` instead collects `fizz_slice_view::caption_view` for each chicken, and `main.js` reads them through `caption_count`, `caption_word`, `caption_x`, `caption_y` (the chicken's feet in picture pixels), `caption_progress` (0 to 1 of the 57-tick life) and `caption_colour` (the bright colour) and shows each as text in `#caption-layer` over the canvas, `aria-hidden` because it stands in for a sound. The text follows Fizz 1's `engine.js`: bold italic Space Grotesk (loaded from Google Fonts, with a bold italic sans as the fallback), 15 px where a tile is 54 px on screen, scaled with the tile's size on screen between 11 and 40 px, a 0.5 px black stroke and a 2 px black shadow, a pop from 0.8 to 1.05 times its size, a rise to 1.8 lines above its anchor and a fade out. Which captions exist and for how long is the shared function's; the blink and the dark colour are the DOS picture's only. The hashed cluck timer and draw count are what set them, so any divergence shows in the hash first. `World::chicken_views()` is the read-only accessor for presenters: each chicken's position, facing, `cluck_age` and `cluck_variant`. The Web presenter's `take_effect` queue still returns the variant only; the chicken index is available from `World::events()` for a presenter that needs it, such as one that pans the sound.

The Web page also draws a HUD over the picture, as DOM in `#stage` (`#play-hud`, below the H panel and its toast, above the captions), in Fizz 1's desktop HUD look and the DOS HUD's layout, the Two-Row Stack (see [The DOS HUD](#the-dos-hud)): a dark rounded glass panel (`rgba(12, 12, 16, 0.82)`, 12 px corners; the picture shows through) in a two-column grid of dim `Fizz`, `Score` and `Deaths` labels each beside a big pixel number, with the key tray in the fourth cell, set in Fizz 1's pixel font (`web/fonts/fizz-regular.woff2` and `fizz-mono-bold.woff2`, copied from Fizz 1 at `4bce036` with its OFL licence). The type is a whole-number scale of the stage height as in Fizz 1 (`pixelScale`: 2 under 480 px, 3 up to 900 px, 4 above; the stage is 13 tiles tall, so this is a rule of the tile's size on screen). The Fizz number is light magenta (`var(--fizz)`, the `--fizz` property on `:root` in `web/style.css`, which `crates/fizz-view/src/theme.rs` pins with a test) and light red at zero, with a black outline of one font pixel on all eight sides (light red at zero is 3.73 to 1 on the glass over white, 2.74 to 1 on DOS without it), and counts stop at 99. The score is five yellow digits in `Fizz Mono` with the leading zeros at 28 percent opacity, held at 99999; for a second after a snack the word `Score` and the `+N` share one grid cell and swap by visibility, so the box never changes size (the Fizz and Deaths numbers are two digits wide always). The tray has a `.sock` for each of the four key kinds (`KEY_KINDS` in `web/hud.ts`), hidden when the level lacks the kind (the slice shows red and blue), each holding both drawings of the 7 by 7 key from `assets/sprites/ep2-hud-keys.json` (`KEY_ROWS`, kept equal by `web/hud.test.ts`) as inline SVG: a dim edge when empty, the key in colour when held, and a ring of four white `drop-shadow`s one key pixel wide for the pickup moment, with white pips under a socket for two to four of a kind and a digit over it for more. There is no CSS animation or transition: the page draws what the module says. Everything the HUD shows beyond the old Fizz and Deaths comes from `App::hud_view`, 16 integers (Fizz, the score shown, the `+N` points or 0, deaths, then in-level, held and ring for each kind) from `fizz_slice_view::HudAnim`, fed by the same step as DOS's; Motion Reduced is `set_shake(false)`, which makes the score jump and shows no ring. `web/hud.ts` is the DOM-free part (text, the score field, scale, the key drawings, change detection, the announcements, the corner choice) and has `bun test` cases; `main.js` writes the DOM only when the view changes and measures the HUD only on a resize. The HUD is `aria-hidden`; a separate visually hidden `role=status` live region says "Out of Fizz", "Red key picked up" (or the kind's name) or "Deaths n" when that happens and nothing else, so it stays quiet; the score is not spoken. The current values are in the H panel's `#hud` lines, which also keep `TICK` and `HASH` for parity inspection. If Ben's sprite comes within a quarter tile of the HUD it crosses to the other top corner (`App::ben_box`, from `fizz_slice_view::ben_view_box`, view only). `tools/check-web-hud.py` plays the golden replay at 1920 by 1080, 1280 by 720 and 540 by 1140 and checks the HUD against the panel on every tick, that the box is one size throughout, the pops, the rings and the score against the replay, and against Ben's box.

Departures from Fizz 1:

- Any velocity with a magnitude below 2^-1000 snaps to zero at the end of Ben's move. Fizz 1 lets an idle pogo's horizontal drag decay for ever, which reaches subnormal values where x87 at 53 bits and SSE2 differ. No golden trace changes with the snap, and a unit test runs an idle pogo for 30,000 ticks.
- The red and blue doors are switched tiles on channels 1 and 2 (solid while the bit is set) rather than solid tiles that Fizz 1 rewrites to empty space. Which key opens which door is level data, a **lock** rule (`rules.rs`, trigger 1 of the `LEVL` rule records): a key colour and a switch channel. Opening follows Fizz 1's rule: with the key of its colour, touching a switched tile on the lock's channel in front of Ben at body height (the tile at `py + 0.2`) while that channel is on opens it (channel off), spends the key (`WorldFlags::KEY_RED_USED` or `KEY_BLUE_USED`, values 2 and 16) and emits `Event::DoorOpen`. A lock works on any switched tile's channel, and only while the door is closed. Locks run in rule order inside Ben's contacts (the order Fizz 1 tries the colours: red, then blue), after the hazards and the exit and before the keys are taken. `World::new` and `set_key_blue` no longer touch a channel: the level's `switches` word is the start state, which a death restores (`World::set_switches`, `World::start_switches`). Triggers other than the lock are refused by `world_from_view` until their phase exists.
- A death respawns Ben in place after Fizz 1's 1.4 s instead of reloading the level, but the respawn resets the level exactly as starting it would: the switch channels return to the level's start state (an opened door closes again), the keys leave Ben's hands and the spent marks are cleared (every key lies where it began), the snacks are put back (Fizz 1 reloads the level, and its score with it), the chickens, the shots and the ammo (5) start over, and `deaths` counts the respawns. An open door no longer survives a death, which is closer to Fizz 1's reload; the golden does not move because the replay's one death (on the spikes, carrying the red key) comes before any door opens.
- The Gloop's "stray" reset (sent home after three seconds more than four tiles off its floor) is not ported; the slice's chicken cannot leave its floor. It would need a hashed timer.
- The chicken's cluck timer and stream are new in Fizz 2; Fizz 1's Gloop is silent. They are described under Events and clucks above.
- The look offset is new in Fizz 2 (see Looking up and down). Fizz 1 keeps the same memory in its camera position. Its up and down aim, the look timers and `aim` are ports and have no departure.
- Mantle is not ported, so nothing starts one automatically. The trace tool refuses scenarios that would trigger it, and the port documents the omission where Fizz 1 calls `tick_mantle`. Ladders, vines, wall kicks, lifts and conveyors under Ben are also not ported.

### Looking up and down

Fizz 1 (`world.rs`, `tick_ben_move` and `step`) counts `look_up` and `look_down` while Up or Down is held alone and Ben is idle (on the ground, not on the pogo or a ladder, no horizontal input), and resets the timer to 0 otherwise. Its camera acts on them after 0.2 s. It has two modes. `CamMode::Side` only honours `look_down` (aim point 3.6 below Ben's feet instead of 1.6 above, with a look-ahead of 1.5 tiles in his facing and a vertical chase of 3.5 per second). `CamMode::Tower`, for tall levels, honours both: 3.6 above or below his feet instead of 0.8 above, no look-ahead, a vertical chase of 8 per second. Both chase exponentially (`cam += (target - cam) * min(rate * dt, 1)`) and clamp the camera to the map. The slice's 32 by 48 maze is a tall level, so the Tower mode is the one to match.

Fizz 2 ports the timers exactly (`Ben::look_up`, `Ben::look_down`, in the same place and order, proved by the `look` trace) and the shot's `aim` (`Ben::aim`, proved by the `aim` trace). The camera is Milestone 1's stateless one, so the exponential chase is replaced by a rule that depends on Ben's state alone, with no `exp` and no camera position to carry between ticks:

- `Ben::look_target` is zero until the timer passes `LOOK_DELAY` (0.2 s), then rises linearly over `LOOK_RAMP` (0.35 s) to `LOOK_REACH` (3.6 tiles) up for `look_up` or down for `look_down`. Fizz 1's chase at 8 per second covers 95% of its distance in `ln(20) / 8` = 0.37 s, so a straight ramp of 0.35 s arrives at about the same time as the eased one.
- Releasing resets the timer, which would snap the view back, so Ben keeps `look_offset`, the stateless camera's memory: each tick it moves toward `look_target` by at most `LOOK_RATE` (12 tiles a second, a little above the ramp's own 10.3). While a button is held the offset equals the target; after a release it returns to 0 in about 0.3 s. It is one `f64` updated in the rules tick beside the timers and is hashed with them.
- The view adds `look_offset` to the middle of Ben's body before `fizz_view::follow` clamps it to the map, so the view never leaves the map and, since 3.6 tiles is well inside half the 200-pixel view, Ben never leaves the screen.

The reach is measured from the middle of Ben's body, where Fizz 1 measures from his feet (its up-aim of 3.6 sits 2.8 above the baseline aim of 0.8, and its down-aim 4.4 below it); the stateless camera is not meant to be a copy of the Fizz 1 camera, and the eased camera is Milestone 3. Up and Down reach the rules as `Buttons::UP` and `Buttons::DOWN` through the same key tables as the other buttons on Web and DOS (the arrows in both layouts, and `W` and `S` in Modern), so no input change was needed.

## The hardware abstraction layer

`fizz-hal` mirrors the shapes of Desk's hardware abstraction layer. It is written in this repository, not vendored and not a path dependency, so the real Desk crates can replace it later.

| Area | Contents |
| --- | --- |
| Time | `Ticks`, the `Clock` trait, and `Pacer`, an integer accumulator that turns a clock reading into whole 60 Hz ticks with a catch-up cap |
| Input | `KeyCode`, `KeyEvent`, the `InputSource` trait and `Set1Decoder` for Set 1 scancodes (extended arrows, WASD, Z, X, C, Space, Esc, and Ctrl and Alt, where the extended right-hand keys report the same codes as the left) |
| Video | `Rgb6`, `ModeInfo`, `HalError` and the `Display` trait |
| Hand-off | `SpscRing`, a bounded single-producer, single-consumer queue between an interrupt handler and the game loop |

The crate is `no_std` with no dependencies, denies `clippy::float_arithmetic`, and denies `unsafe_code` everywhere except `ring.rs`.

- **Deliberate deviation from Desk.** `Display::present(pixels, pitch)` takes the finished frame and replaces Desk's frame-buffer and `MmioRegion` pair. The HAL therefore contains no pointer to video memory and no `unsafe`; the DOS adapter owns that boundary.
- **`SpscRing`** is the only `unsafe` in the HAL. It is adapted from Desk's `ring.rs` and uses only atomic load, store and swap. DOSBox with `cputype = 486` rejects `CMPXCHG`, so `clippy.toml` bans the compare-and-swap family of methods.
- **Second consumer.** `WebClock` and the DOS `DosClock` both implement `Clock` and share `Pacer`, which is what proves the trait. `WebClock` rounds `now_ms` up so a 60 Hz display never loses a tick to truncation.

## The DOS runtime

`dos/rt` (`fizz-dos-rt`) is self-contained and does not depend on `fizz-hal`. The HAL adapters live in `dos/fizz2/src/hal.rs`. The runtime keeps a tiny local byte ring in `rt/src/ring.rs` for keyboard bytes, to avoid the dependency.

- **Build.** Cargo links an ELF with `rust-lld` and `dos/link.ld`. `tools/elf2go32.py` packs it, with the DJGPP stub, into a go32 executable that loads under CWSDPMI. No C compiler or C library is involved.
- **Timer.** The PIT is programmed to divisor 19886, which is 60.0011 Hz. A 16-bit accumulator adds 19886 per interrupt and, when it wraps past 65536, chains to the BIOS handler. The BIOS clock therefore keeps 18.2065 Hz and the DOS time of day stays correct. The divisor is restored to 0 on exit. `/REPLAY`, `/LIVE` and `/PANIC` run the timer at divisor 2131 (559.9165 Hz) instead, started by `audio::start`, because `fizz-sfx` times its OPL data in 560 Hz ticks (`OPL_TICK_HZ`) and the audio service steps them from the interrupt. The accumulator is the same design with the divisor in a static: it adds 2131 per interrupt and chains to the BIOS handler on each wrap past 65536, which is every 30.75th interrupt, so the BIOS clock still keeps 18.2065 Hz (`BIOS TICKS 510` for the 1,681-tick replay, inside the 508 to 512 bound; the count is taken with the wrap at midnight in mind, 1,573,040 BIOS ticks a day, because a CI run that crossed midnight once printed 4,293,394,766). The simulation stays at 60 steps a second: `DosClock` reports 559,916 millihertz and the integer `Pacer` turns that into steps with an exact remainder. `/BENCH` keeps the 60 Hz timer, because its stopwatch repairs a one-period dip that would be 9 times as likely and as long as a section at 560 Hz; its figures therefore do not include the audio interrupt. The extra interrupts cost one stub, one handler call and, on a tick that has a write due, about 40 port reads per OPL register. None of that cost has been measured on a 486, and the effect on the `/BENCH` budget is not known.
- **Frame rate.** The simulation always steps at 60 Hz through the integer `Pacer`; only the drawing cadence changes, so the transcript, the input and the audio are the same at every rate. `fizz_machine::FrameGovernor` (`crates/fizz-machine/src/governor.rs`, `no_std`, pure) decides: `new(mode)` with the mode `/FPS30`, `/FPS60`, `/FPSAUTO` or `FIZZ2.CFG`'s frame-rate byte gave (`FrameRate::Auto`, `Hz30`, `Hz60`), `rate()` (60 or 30), `draw_this_tick(tick) -> bool` (always at 60; at 30 once two ticks have passed since the last frame drawn) and `record_frame(cost_ticks_560) -> Option<u32>`, which in Auto adds the cost of a drawn frame and, when the 32nd arrives, returns the window's average as a percentage of a 60 Hz frame and may change the rate. The fixed modes never measure and never change. The percentage is `spent * 60 * 100 / (32 * 560)`, where a sixtieth of a second is 9.33 ticks of the audio service's 560 Hz clock. Above 100% and up to 170% it chooses 30 Hz; above 185% or below 67% it chooses 60 Hz; from 170% to 185%, and from 67% to 100% at 30 Hz, it keeps the rate it has (the dead bands: dearer than 185% a cap would only throw frames away, and the bands stop it flapping). Auto starts at 60. Precedence is that of the sound settings: a flag, else the file's byte, else Auto; the last flag wins; flags never write the file (`dos/fizz2/src/frames.rs` and `sound::frame_rate`). A drawn frame's cost is the span of `timer::ticks()` around the draw, the retrace wait (once per drawn frame, so at 30 Hz once per two steps) and the copy in `/LIVE`, and around the draw and the copy in `/REPLAY`, which does not wait. `/LIVE` and `/REPLAY` print `FRAMES <n> TICKS <t> RATE <hz> MODE <auto|30|60>` after the platform lines; `/BENCH` is unchanged. The policy and the thresholds are adapted from Fizz 1's DOS port (fizz-dos `m4/c/main.c`, commit `221dd6c`: `if (rate_now == 30 && t < drawn + 2) continue`, the 32-frame window, 100/170/185/67); its detail setting is not taken because Fizz 2 has no backdrop layers. The owner's decisions: the performance floor is a 486DX2-66 (DOSBox at 26,800 cycles), the 30 Hz judder is accepted and there is no interpolation. At 26,800 cycles a drawn frame costs about 3.5 ms (draw 2.9 ms and copy 0.6 ms, `/BENCH`), about 21% of a sixtieth of a second, so Auto stays at 60; at 4,500 cycles it costs about 21 ms (125%) and Auto settles at 30 (`tools/check-dos.sh` runs both). In `/LIVE` the measured cost includes the retrace wait, which on a 70 Hz mode 13h screen adds anywhere from nothing to one refresh (about 14 ms), so a cheap frame measures well above its drawing cost there; that follows Fizz 1, which also times its vertical-sync wait, and whether the thresholds suit a real card is unmeasured.
- **Interrupts.** The IRQ handlers share one locked interrupt stack, so handlers never nest. Each returns `Action::Eoi` or `Action::Chain`. Handlers do bounded work, allocate nothing and never use the x87.
- **No `hlt`.** The instruction is privileged under CWSDPMI. Pacing is a volatile spin on the tick counter.
- **Keyboard.** The runtime owns IRQ1 and decodes Set 1 scancodes. It restores the BIOS keyboard flag lock bits at `0x417` and clears `0x418` on exit.
- **Video.** Mode 13h is set through DPMI function 0300h, a real-mode `INT 10h`. In `/LIVE`, `FIZZ2.EXE` calls `Display::wait_vretrace` once per drawn frame, just before `present`, so the 64,000-byte copy begins at the start of the vertical retrace and the picture does not tear (the method Fizz 1's C port uses, `vga_vsync`). The wait polls bit 3 of port 3DAh, first until any retrace in progress ends and then until one begins, each phase bounded at 1,000,000 reads, so a machine or emulator whose status port never toggles costs a frame's time and not a hang. It only delays the copy: the simulation is still paced by the timer through `Pacer`, and the retrace adds no ticks. `/SLICE` and `/REPLAY` do not wait. Tearing cannot be seen headlessly, so the effect is unverified on real hardware.
- **Probes.** `rt/src/probe.rs` finds what the machine has: the display adapter (INT 10h and INT 11h through `dpmi::simulate_int`), a mouse driver (INT 33h, only when its real-mode vector is not null), the game port, the FM chip at 0x388 (OPL2, OPL3, or two OPL2 on a Sound Blaster Pro 1), the Sound Blaster DSP and its version, the x87, the processor family (the EFLAGS AC and ID bits; CPUID is never executed) and free physical memory (`dpmi::free_memory_info`, DPMI 0500h). They run before the timer is hooked. `rt/src/pit.rs` supplies `delay_us`, a wait on the latched PIT channel 0 count that is valid only at the BIOS rate and so refuses to run while the 60 Hz timer is hooked; every wait on a device is bounded, so an absent card costs milliseconds and not a hang. `fizz-machine` gives the results their meaning, and `docs/DOS-CHECK.md` lists each method, its failure modes and what DOSBox showed.
- **Audio.** `rt/src/audio.rs` is the sound service. It also steps the level music (`fizz-music`'s `MusicPlayer`) from the same 560 Hz handler, before the effect and through the same register write, with `fizz_machine::route` applied by stream kind (see [`MUSIC.md`](MUSIC.md#the-dos-audio-service-built)); `/BENCH /AUDIO` runs it under the bench, with the handler's time latched from the PIT. It plays the effect of every event that has a sound (`play_events` in `FIZZ2.EXE`, from `fizz_slice_view::event_sound`) on OPL2 channel 5 (the distance in its carrier level), on the OPL3 pair of channels 5 (left output) and 14 (right output) with a level for each side, or through the PC speaker (no placement), or does nothing. The program works the placement out with the pure integer `fizz_sfx::place` function and hands the interrupt handler three small attenuations, so the handler does no arithmetic of that kind and the DOS crates keep to no float arithmetic. The pair doubles an effect's register writes (the busiest tick goes from 11 to 22 writes). The service has one effect slot, so the last request of a tick is the one that starts and a later effect cuts an earlier one off, as in Fizz 1's DOS port. It is described in [`SOUND.md`](SOUND.md#the-dos-path). Its state belongs to the interrupt handler alone, the program reaches it through atomics, and `stop` is on the clean-up list so a panic silences the chip and puts register 0x105 back to 0. The design follows Fizz 1's `m4/c/sound.c` (the register write timing, the speaker through PIT channel 2 and port 0x61, requests taken up by the handler), read only, and `audio.rs` says so in its header. The service runs under DOSBox with the OPL2, the OPL3 and the speaker, and a recording of its output is not silent where the `/NOSOUND` one is. `audio::replan(&Resolved)` changes the music and effects devices while the service runs (called from the program with the handler's active flag clear, so the handler never sees a half-built state; it silences the old plan, switches OPL3 mode off or on to match the new one, closes the speaker gate when leaving the speaker and starts the music again from its prelude); `/REPLANTEST` walks eight plans through it and `tools/check-dos.sh` checks the counters and the chip and gate state in DOSBox (see [`SOUND.md`](SOUND.md#changing-devices-while-the-game-runs)). That is all that has been verified: how it sounds, and whether the timings are right for a real OPL2, a real OPL3, a real Sound Blaster and an ISA bus, has not been tried. That includes a live switch: nobody has listened to one, in DOSBox or on hardware.
- **Clean-up.** Every vector is restored on exit and on panic through the clean-up list. A panic exits with code 3.
- **File names** are 8.3 and upper case.

`FIZZ2.EXE` takes one mode argument, and every switch it accepts is one line of the table in `crates/fizz-machine/src/switches.rs` (name, argument shape, help line, group, hidden flag, what it does). `main` calls `switches::parse` on the arguments and `switches::write_help` for the help, so the parser and the help cannot disagree; a host test fails if a switch has no help line or a help line names no switch, and `crates/fizz-machine/tests/help.txt` holds the exact text (25 lines, plain ASCII, at most 79 columns; `BLESS=1 cargo test -p fizz-machine --test help` rewrites it). The table is `no_std` and pure, in `fizz-machine` beside `settings`, whose `apply_flags` it calls to check a sound value. `/?`, `/HELP` and `-?` print the help and exit 0 before any hook or video mode change, whatever else is on the line; an unrecognised argument (a switch, a bad sound value, or a number other than after `/BENCH`) prints `FIZZ2.EXE: unknown switch <arg>, try FIZZ2.EXE /?` and exits 2, where it used to start `/LIVE`. Adding a switch is one table line plus the code that acts on its `Kind`. `/PANIC`, `/CFGTEST` and `/OPTIONS` are hidden developer switches. `/LIVE` plays the slice from the keyboard, ends on Quit to DOS in its Paused menu (Esc opens it), and is the default; it also ends by itself after 30 seconds of wall-clock time (`LIVE_SERVICE_CAP`, 16,800 ticks of the 560 Hz service clock, so a run left in a menu ends too) so an emulator run cannot hang, and prints `LIVE TICKS`, `MOVED` (Ben is off his spawn) and `VECTORS RESTORED`. `/REPLAY` plays the slice script (1,681 ticks, about 28 seconds), drawing it as it goes, and prints the `SLICE REPLAY 1` transcript, `EXIT yes` when Ben reached the exit, `FPU CW 027F`, `BIOS TICKS <n>` (510 for the script) and `VECTORS RESTORED yes`; it is the DOS leg of the parity gate. The transcript is collected in an 8,192-byte buffer and printed only after the screen is back in text mode. `/MODERN` selects the modern key layout and `/KEEN` the Keen one, each over `FIZZ2.CFG`'s keys byte, and either combines with `/LIVE` or stands alone for it. `/CHECK` shows the read-only start-up check on the 80x25 text page (B8000h, or B0000h on a monochrome adapter; `rt/src/text.rs`, keys through INT 16h), before any hook: Esc exits 0 and Enter goes on to `/LIVE`. It waits for a key, so no script runs it (a host test greps the scripts). `/CHECKCELLS` draws the same screen, reads the 4,000 bytes back from video memory and prints them as `CELLROW` lines, which `tools/check-dos.sh` compares with the host builder for six machines. `/PROBE` runs the probes before any hook, prints `PROBE <key> <value>` lines, `CELLS <hash>` (the hash of the check screen those values make), `HEAP`, `PAGES FREE` and the platform lines (`EXIT yes`, `FPU CW 027F`, `VECTORS RESTORED yes`), needs no key and draws nothing. The sound flags (`/MUSIC:x`, `/FX:x`, `/ADLIB`, `/SB`, `/SPEAKER`, `/NOSOUND`) are switches like `/MODERN`, not modes; with `FIZZ2.CFG` they give the `SOUND` line that `/LIVE`, `/REPLAY` and `/PROBE` print after the screen is back in text mode (`dos/fizz2/src/sound.rs`; see [`DOS-CHECK.md`](DOS-CHECK.md#settings-file-and-flags)). The probe runs before the timer is hooked, so those two modes probe first. `FIZZ2.CFG` is read from the current directory through `dos::File` and written by `sound::save`; the file is version 3, 13 bytes (version 1 and 2 files are still read; the byte table is in [`DOS-CHECK.md`](DOS-CHECK.md#settings-file-and-flags)). `/CFGTEST` is a hidden test mode that saves, reads back and prints the file. `/NOCAPTIONS` turns off the in-world cluck captions and `/CAPTIONS` turns them on again (the default); the last of the two on the command line wins, and either combines with any mode. Each overrides the captions byte of `FIZZ2.CFG` for the run, so a saved Off is turned back on by `/CAPTIONS`; with neither switch the file's choice stands, and On is the default. The Web page has a Captions row in its Options screen and the V key (neither layout uses V), on by default and remembered in the `fizz2-options` blob in `localStorage`. Captions gate only the text; the chicken's beak moves regardless. `fizz_slice_view::draw_slice_with(.., &DrawOptions { captions })` is where the DOS picture applies the choice (the Web page applies it by not showing the text), and `draw_slice` means captions on, so the parity gate's hashes (which never see a picture) are unaffected. `DrawOptions` also has `shake`, on by default, which is the Motion setting (Full or Reduced) and gates two effects. The second is the death spin: while Ben is dead his sprite is turned about its centre by 8 radians a second (Fizz 1's `rot += 8 * dt`), counter-clockwise on screen, from the ticks since the death, read from `Ben::dead` alone like the shake; it is nearest-neighbour inverse mapping in integers (`blit_sprite_turned`) from a baked table of `cos` and `sin` times 4096 per tick, so no float sine runs and Web and DOS draw the same pixels. A spinning Ben does not flicker; with `shake` off he is drawn as before, the flat flipped jump pose flickering. It costs about 0.6 ms per death frame under `/BENCH` (85 of the script's 1,268 frames), and the state hash and `EVENT` lines do not change. The shake: for the 18 ticks after Ben dies it offsets the camera's X by a baked table of at most one pixel (Fizz 1's `sin(t * 70) * shake * 0.15` tiles, with `shake` 0.6 falling 2 a second, rounded to whole pixels), derived from `Ben::dead` alone, then `follow` clamps to the map as usual. It is a view effect, so the state hash and `EVENT` lines do not change; the one pinned frame that moved is tick 400, a death frame, in `fizz-slice-view`'s digest test (and again for the spin, whose ten death frames are pinned in both settings), and the DOS and host frame digests still agree. DOS passes `shake: true` when `FIZZ2.CFG`'s motion byte is Full (the default) and `false` when it is Reduced. The same file's placement byte chooses how DOS places clucks: Enhanced (the default) pans and fades them by where the chicken is in the view, and Classic plays every cluck centred at full volume. The Web `App` has `set_shake` and `shake`; the page's Motion row (System, Reduced or Full) calls them, remembers the choice in the `fizz2-options` blob, and System, the default, follows `prefers-reduced-motion: reduce`. Web captions are page text and do not shake with the picture. `/PANIC` hooks IRQ 0 and panics, to show that the clean-up list runs.

### Key layouts

The two layouts are exclusive sets, and Keen is the default on both platforms. Keen is Fizz 1's classic layout: the arrows move, Ctrl is `JUMP`, Alt is `POGO` and Space is `FIRE`. Modern is the arrows or `W` `A` `S` `D` for movement, `Z` for `JUMP`, `X` for `POGO` and `C` or Space for `FIRE`. Arrows work and Space fires in both; a key of the other layout does nothing.

On DOS, `fizz_present_dos::key_to_buttons(KeyCode, Layout) -> Option<Buttons>` is the one mapping, with `Layout::Keen` (the default) and `Layout::Modern`. `FIZZ2.EXE /MODERN` picks the second, `/KEEN` picks the first over a saved Modern, and with neither the layout is the one `FIZZ2.CFG` holds (Keen when there is no file). The decoder reports Ctrl and Alt for both the left and right keys. A Pause sequence is swallowed whole, including its `1D`, so it never looks like a Ctrl press.

On the Web, `web/main.js` holds the same two tables keyed on `event.code` and feeds button bits to `App::key`. The Keys row of the Options screen switches layouts and the choice is kept in `localStorage` when it is available (see [The Web Options screens](#the-web-options-screens)). The page calls `preventDefault` for every key the active layout uses, which also keeps Alt from focusing the menu bar. A tab still cannot block every browser shortcut (Ctrl+W closes it) or the window and workspace shortcuts of some desktops, so the Modern layout avoids Ctrl and Alt.

In fullscreen (the `F` key or the Options screen's Fullscreen row), the page calls the Keyboard Lock API, `navigator.keyboard.lock`, with the keys of both layouts, and releases it when fullscreen ends. Chromium supports it; where the API is missing or refuses, the page plays on without it. Esc is left out of the lock so the browser's way out of fullscreen keeps working.

### The DOS HUD

The slice's heads-up display is a translucent pill in the top-left corner of the 320 by 200 picture, the Two-Row Stack (`crates/fizz-present-dos/src/hud.rs`: 120 by 27 pixels at (4, 4), 3,240 pixels, a bit over 5 percent of the picture, with corners rounded by 5 pixels like the Web HUD's; it was 72 by 27 with `Fizz`, `Deaths` and one key chip, 1,944 pixels, before the score and the tray). It follows the box Fizz 1's DOS port draws (`hud()` in its `shell.rs`): a light grey outer edge, a dark grey inner edge and rows of text in Fizz 1's proportional pixel font with a one-pixel black shadow, over a picture that is dimmed and still visible. The port does that with `ui::dim(frame, x, y, w, h, 9)`, which lowers each byte's brightness level by nine of its fourteen (a level is `(level - 1) / 13` of the colour, so level 5 is 4/13, about 31 percent). The frame here is mode 13h, which has 256 palette entries, so `dos_palette()` gives the display the sixteen EGA colours in entries 0 to 15 (unchanged, so every picture and the one-byte-a-pixel frame stay as they were) and the same sixteen at 4/13 of their brightness in entries 16 to 31. The cached strip is an overlay with two special values: `TRANSPARENT` (the picture shows dimmed: each covered pixel becomes `16 + its colour`) and `OUTSIDE` (beyond a rounded corner: the picture is untouched). Each frame composites the strip over the picture with a per-word mask, `(word & keep) | set`, 30 words by 27 rows (810 word operations, about 1.7 times the old box's 486, and no new palette entry); the strip is rendered only when the view changes. The edge, text and keys draw in full colours on top. What it shows is `fizz_slice_view::HudView`, the model the Web page reads too (`crates/fizz-slice-view/src/hud.rs`). Row 1: `Fizz` and its number at x 5, light magenta (`FIZZ_INDEX` in `fizz-view`'s `theme.rs`) or light red at zero, drawn with a black outline on all eight sides instead of the shadow, so the ink always sits against black; then at x 50 the word `Score` (or the yellow `+N`, right-aligned to the digits, for the 60 ticks after a snack) and at x 83 five yellow digits in 6 pixel cells, the leading zeros dark grey. Row 2: `Deaths` and its number in white, and from x 60 the tray: one 7 by 7 socket every 10 pixels for each key kind the level has (`assets/sprites/ep2-hud-keys.json`), the key's pixels when held and the sprite's edge pixels in dark grey when empty, a white ring (the silhouette dilated by one pixel, drawn for 12 ticks after the pickup) round a key just picked up, and white pips two pixels apart on a row under a socket for two to four of a kind (a digit over the key for more). Contrast over the brightest picture colours (white and yellow at 4/13 are grey 19 of 63): light grey labels about 3.8 to 1, white numbers and yellow digits over 7 to 1, the light magenta Fizz number about 3.3 to 1, each with its black shadow; light red at zero ammo is 2.7 to 1 over dimmed yellow, under the 3.0 floor, so the Fizz number's black outline is what it sits against: 6.7 to 1 over black. A test pins every floor, and that each ink pixel of the Fizz number has only ink or black round it. The dark grey leading zeros are meant to recede, as the Web's 28 percent opacity ones are. The Web presenter does not draw this box; it converts indices through its sixteen-colour table with `& 15`, which is in range for any byte, and `frame_digest` and the `frames` example hash the bytes whole. Numbers show at most 99, the score at 99999 (the game keeps the true score); there is no lives line (the slice has none, so `Deaths` takes its slot) and no tick: `TICK` stays in `/BENCH` and the transcripts, and on the Web in the panel's text lines, which are not this box. `cargo run -p fizz-present-dos --example hudshot -- <dir> <tick>...` writes the slice at the given ticks as PPM files to look at it.

The box is a cached strip. `Hud` keeps the rendered 120 by 27 pixels and the `HudView` (Fizz, the score shown, the `+N`, deaths and the four sockets) they were rendered for; `Frame::draw_hud` renders again only when the view differs from the last call's, then copies the strip's 27 rows into the picture, which is redrawn from scratch every frame. A view that changes and changes back renders twice and leaves the picture as it was. A snack makes it render every second tick while the score counts up (a cookie takes 10 ticks), and a key pickup for the 12 ticks of its ring. `ViewFx` carries the animation (`HudAnim`, fed by `observe` after every step with the Motion setting); a presenter that never observes draws the world's own score with no pop or ring. None of it is hashed: the score is worked out from the snacks taken and the rest is view state, so the state hash, the transcript and the golden are unchanged. The exit banner (`LEVEL CLEAR`) and the check and probe screens keep the 8x8 capital font.

`/BENCH` at 26,800 cycles a millisecond, the whole script, drawing average (the maximum is the worst frame, which is a death or a shot): before, the strip of 8x8 text redrawn every frame, 2,802 us (maximum 3,568); after, 2,229 us (maximum 3,340). Leaving the box out altogether gives 2,196 us, so the box costs about 33 us a frame on average, almost all of it the copy of 1,944 bytes, against about 606 us for the old strip and its four texts. The step (108 us) and the copy to the screen (599 us) did not move.

The frame digests (`BENCH FRAME`, eleven ticks) now cover the whole frame instead of the picture below a 10-row strip: the strip is gone, so the top rows are picture, and the box is part of what is proved. Every one of the eleven changed when this box replaced the bar, deliberately, and the DOS and host digests agree. The digests pinned in `fizz-slice-view` cover the picture alone and did not change, nor did the state hash `0edebb797e63edff` or any `EVENT` line.

### The DOS menu screens

The Options and Paused screens are drawn by `crates/fizz-present-dos/src/menu.rs` from the `RowList` that `fizz-menu` returns, in Fizz 1's DOS look (`options_screen` and `plate_rows` in its `shell.rs`). The layout is for the 320 by 200 frame this presenter owns; the Web draws its own overlay. The whole frame is dimmed once, when the screen opens (`MenuView::open`): every pixel `p` becomes `16 + (p & 15)`, the dimmed half of the palette the HUD box already uses (a pixel that is already dimmed keeps its colour), and the result is a second `Frame` held by the `MenuView`. Each redraw copies that background into the frame being presented and draws on top, so the picture beneath never changes while the screen is up. `draw_options`, `draw_paused` and `draw` return whether they drew: they compare a digest of everything the screen shows (heading, footer, the note, the can's height and every row's label, value and selection) with the last draw's, and a key that changed nothing, or any tick within the same 20-tick half of the bob, draws nothing and asks for no copy to the screen. `open` and `invalidate` force the next draw.

The geometry, in pixels: the heading is white in the pixel font at 2x (`pfont::draw_text_scaled`) with a black shadow, centred, its top at y=22, with a one-pixel rule in the Fizz colour across x 40 to 279 at y=36 (the 'p' of Options reaches the rule's row and is drawn over it). Rows start at y=56 with a pitch of 14. The column is x 40 to 279: the left 18 pixels are the gutter and the plate takes the rest (x 58 to 279). The chosen row is a solid plate of the Fizz colour 12 pixels high with its four corner pixels left out, with its label at 6 pixels in and its value right-aligned 6 pixels from the right edge, both in black. Fizz 1's soda can (the `soda` sprite, exported from Fizz 1 and recoloured grape: a light magenta body with white bubbles) stands in the gutter at x=40, two pixels above the row, and rises one more pixel every 20 ticks. The other rows have a white label and a Fizz-coloured value, each with a one-pixel black shadow. When a row shows `*`, a grey note (`OVERRIDE_NOTE`) is at y=172, and a grey footer is centred at y=186: "Up/Down choose, Left/Right change, Esc back", or on Paused "Up and Down choose, Enter selects, Esc resumes". The pixel font has no arrows, so none are drawn. A test over every row of both platforms, every choice, every machine kind and every override marking checks that a label and its value fit the plate with a space between them, and that the note, footers and headings fit the frame. The screens are tested by pinned frame digests of Paused, each selected Options row, a `*` row and a missing-device row over a synthetic picture; the `MenuView` and a picture are about 130 KB, so the caller should keep them in a `static` or the heap rather than on the 256 KB stack with more.

`FIZZ2.EXE /MENUSHOT` (a hidden developer switch) draws the two screens over the slice's first frame (the Options screen with the cursor on Effects, the Frame rate row starred and a Sound Blaster 16 machine, then the Paused screen), presents each and prints `MENUSHOT options <digest>` and `MENUSHOT paused <digest>`. The host's `menushot` example (`cargo run -p fizz-present-dos --example menushot [dir]`) prints the same lines, and with a directory also writes `options.ppm` and `paused.ppm` in the DOS palette; `tools/check-dos.sh` requires the two sets of lines to be equal, so the DOS build is proved to draw the pixels the portable code does.

The `/LIVE` flow is `dos/fizz2/src/menu.rs` (`Menus`), driven from `live` in `main.rs`. Esc in play opens Paused (`PausedScreen`: Resume, Options, Quit to DOS) over the last frame drawn (`MenuView::open` dims it once); Esc or Resume closes it, Options opens `OptionsScreen` over the same dimmed picture, Esc or Back there returns to Paused with the cursor on Options, and Quit to DOS ends the run. Keys come from `fizz_present_dos::menu::menu_key(code, layout)`: Up, Down, Left and Right (with `W` `A` `S` `D` in Modern) move, Enter and the layout's Jump and Fire confirm (and step a choice forward, as Right does), Esc and the layout's Pogo go back; only presses count. `KeyCode::Enter` is scan code `0x1C`, plain or after `0xE0` (the keypad Enter). While a screen is up the loop reads keys and draws, and does not step the world, so the rules, the death and cluck effects and the frame governor are held while the music (the audio service) goes on. Opening and closing clear the `InputLatch`, and closing makes a fresh `Pacer`, so the time spent in a menu is not played back as a burst of steps and a key held across the change is not stuck down. The run's cap is wall time, so the world's tick count stops growing in a menu while the cap runs. `Caps::dos` is built each frame from `resolve(&Settings::default(), &probe)` (what Auto would do on this machine) and `Drawing::rate()`; a row set by a switch (its value differs from `FIZZ2.CFG`'s) is marked in `Overrides`, which gives the star and the note.

Each change applies when the key is pressed: Captions and Motion set `DrawOptions` (`captions`, `shake`), Keys sets the `Layout` the key map uses, Frame rate calls `Drawing::set_mode` (a fresh `FrameGovernor`; the `FRAMES` line then reports the new mode), Sound placement sets the `CLASSIC_PLACEMENT` flag that `play_events` reads, and Music and Effects resolve a plan from the chosen `Settings` against the start-up probe and hand it to `audio::replan`. `FIZZ2.CFG` is written once, when Options is left with a change made (`Values::to_prefs` through `sound::save`); a row a switch still holds is saved with the file's own value, so a switch is never saved. A failed save (`cfgfile::save_bytes` returns the error) sets `MenuView::set_message("Could not write FIZZ2.CFG")`, drawn in light red on the note's line, and the next leaving tries again. The run prints `OPTIONS SAVED yes|no` for the latest attempt, and nothing when none was made. `/OPTIONS` runs the same loop with Options open from the start and ends when it is left. The 64 KB view lives on the heap (`Box`); the mode functions of `main.rs` are `#[inline(never)]` and `Menus::new` too, because inlined they stack their frames (the slice's 64 KB frame, the view's temporary, the `/MENUSHOT` pair) in the program's 256 KB stack and overflow it before the first line prints.

## The Web build

`fizz-present-web` exports one `wasm-bindgen` app, `App`, over the slice's world: it holds `fizz_ep2::level::world()`. `key(bits, down)` records a button change, `frame(now_ms)` runs the whole ticks that have elapsed and returns their count, and `reset()` starts the level again without touching the pacer. `render()` draws the world into a palette-indexed buffer, 208 pixels tall and 96 to 1280 wide as the page asks through `set_view(w, h)` (default 320 by 208; the DOS presenter keeps 320 by 200), with `fizz_slice_view::draw_slice`, the routine the DOS presenter also calls, and expands it to RGBA with the sixteen EGA colours; `rgba_ptr()`, `rgba_len()`, `width()` and `height()` let the page view that buffer in the module's memory (`new Uint8ClampedArray(memory.buffer, ptr, len)`, made again every frame because the memory can move) and `putImageData` it, so JavaScript draws nothing itself. `tick`, `hash_hex`, `ammo`, `has_key`, `deaths`, `door_open` and `exit_reached` feed the page's text HUD, and `hud_view()` hands the in-picture HUD its numbers (see below). `slice_replay_transcript()` returns the transcript `fizz_ep2::replay` writes, which the parity gate runs under Node or Bun. The page's script feeds `performance.now()` and key events in; rules never see the browser clock. Time beyond five ticks per displayed frame is dropped, so a hidden tab does not cause a burst on return. The first tick of each `frame` call takes the key latch's edges and later ticks in the same call see only the held buttons, so a press and release between two frames still reaches the rules once.

The page keeps the view 13 tiles (208 pixels) tall, sets its width from the window aspect (`ceil(208 * width / height)`, limited to 96 to 1280 pixels; the limit is a sanity bound, 1.3 MB of buffers at most), resizes the canvas and calls `set_view` after a debounced `resize` or `orientationchange`, and scales the canvas by the window height over 208 with `image-rendering: pixelated`, a whole number when the height is a multiple of 208. A level narrower than the view is centred by `fizz_view::follow`, with sky at the sides. The view size is reported to the view and camera code only; the rules never read it (no waking, culling or spawning from it), so hashes and EVENT lines match at every size and on DOS (the `the_view_size_never_reaches_the_rules` test). A later scene-intent layer can receive it as view information for culling and drawing. The HUD is page text under the canvas.

`wasm-bindgen` is pinned at `=0.2.125` in `Cargo.toml`, and the command-line tool must match. Install it at user level:

```bash
cargo install wasm-bindgen-cli --version 0.2.125 --locked
```

`App` also queues the sound of each event for the page (`event_sound`: the effect id and where it sounds). `frame` reads `World::events()` after each step it runs (the rules clear the list on the next step, and a frame can run up to five), and `take_effect()` hands out the oldest waiting effect id (0 to 14), or -1 when none is left; the page calls it until it returns -1 after each frame. The queue holds 32 and drops the rest, `reset()` empties it, and nothing in it reaches the rules, the hash or the transcript.

The page's script is bundled with Bun. `package.json` pins `@liminal-hq/undertone` at exactly 0.3.0 from the public npm registry (Fizz 1 asks for ^0.2.0), and `bun.lock` is committed. `tools/build-web.sh` runs `bun install --frozen-lockfile`, which is the build's only use of the network and only on a cold cache, and then `bun build web/main.js`, which writes one minified `dist/web/main.js` holding `web/audio.ts` (the shared audio root), `web/music.ts`, `assets/music/`, `web/sfx.ts`, `assets/sfx/effects.ts` and Undertone. The wasm bindings stay a relative external import, so the bundle works from any base path and runs with no network. Bun is therefore a build requirement, as it already is for the sprite and sound tools; the `ci-dos` image has it and the `parity` job needs no extra step. `bun test web` (the sound player and the music player) runs in that job. `web/options.ts` is in the bundle too. `tools/check-web-sfx.py` and `tools/check-web-options.py` need Chromium and run locally and from `tools/check.sh`.

`tools/build-web.sh` fails, naming both versions, if the installed tool differs from the version in `Cargo.lock`. It writes a static bundle to `dist/web` with relative URLs only, so a launcher (such as Fizz 1's) can bundle it under any path later.

### The Web Options screens

The Web page has two screens over the picture, Paused (Resume, Options, Restart) and Options (Sound, Music, Placement, Motion, Captions, Keys, Fullscreen when the browser allows it, Back), opened by Esc or the Pause key or, for Options alone, by the `Options (Esc)` button of the H panel. The model is `fizz-menu`'s, reached through `crates/fizz-present-web/src/menus.rs` (`Menus`: which screen is up, the `PausedScreen` and `OptionsScreen` with `Caps::web`, the values, the overrides) and `App`'s `menu_*` bindings (`menu_key`, `menu_click`, `menu_step`, `menu_select`, the row accessors, `menu_value`, `set_value`, `set_override`). The words, the rows, the cursor and the wrap rules therefore come from the one crate DOS will also draw from; the page draws only. Escape, `Backspace` and Back mean `MenuKey::Back`; the arrows move and step; Enter and Space mean `Confirm`. Web rows reuse the DOS fields: Sound is `fx` (On is Auto, Off is Off), Music is `music`, Motion's System is `MotionPick::System`, and Fullscreen is in `Values` but not in `Prefs`.

While a screen is up `App::frame` drops the pacer and returns 0, so no tick runs and the first frame after resuming only restarts the pacer: time spent in the menu is never caught up. `App::hold()` does the same on request. The rules, the replay and the state hash never read any menu state (a host test checks the hash is untouched; `tools/check-web-options.py` plays the golden replay with the screens opened and changed in the middle of it and checks `0edebb797e63edff`). The page releases every held key as a screen opens.

`web/options.ts` has two halves. The pure half reads, migrates and writes one `localStorage` blob, `fizz2-options`, `{"v":1,"sound","music","placement","motion","captions","keys"}` with the words `on` or `off`, `enhanced` or `classic`, `system`, `reduced` or `full`, `keen` or `modern`; a field that is missing or wrong falls back to its default alone, and storage that throws gives the defaults. When the blob is absent the six older keys (`fizz2-layout`, `fizz2-captions`, `fizz2-motion`, `fizz2-audio`, `fizz2-sound`, `fizz2-music`) are read once, written as the blob and removed. `main.js` loads the blob into the module with `set_value`, applies every change as it happens (`Sfx.setMuted`, `setMode`, `Music.setEnabled`, the layout with `releaseAll`, `App::set_captions`, `App::set_shake`) and saves after each one; `Sfx` and `Music` are made with no storage of their own. A `?audio=` address is pushed as the Placement value and marked with `App::set_override`, so the row shows `Classic *` and the note `OVERRIDE_NOTE`; it is not saved unless the player changes the row. The DOM half is the overlay, in Fizz 1's Web menu look (`packages/engine/src/menu/rows.ts`, `rows.css` and `tokens.css`): a panel of `rgba(12, 12, 16, 0.82)`, the Fizz pixel font at the HUD's whole-number scale (kept small enough that a row fits a narrow stage), the selected row as a plate in `var(--fizz)` stepping through `#ff55ff`, `#ff77ff` and `#ff99ff` with ink `#1a001a` and Fizz 1's clipped corners, Fizz 1's soda can (a grape body, white bubbles, the same grid as the DOS sprite) bobbing as the bullet, values muted and `◄ value ►` on the selected choice. It is a `role=dialog` with `aria-modal` holding a `role=menu` of `menuitem`s, each with an `aria-label` of the label and value; focus moves to the selected row on open and returns to where it was on close; a `role=status` live region says each change; the plate and the can stop under `prefers-reduced-motion` and when Motion resolves to Reduced. Rows are drawn once per screen and updated in place, so a pointer press is never lost to a rebuild. `web/options.test.ts` covers the pure half; `tools/check-web-options.py` drives the built page.

## Toolchain

The DOS toolchain is the shared `ci-dos` image, pinned by digest:

```text
ghcr.io/liminal-hq/ci-dos@sha256:93d129b5c910b2a2d5de38ae7235e9dc8b311d302c1c57992f060b036a74dc4e
```

It provides Rust 1.98.0 with the `wasm32` and `i586` targets, Bun 1.3.14, DJGPP, DOSBox Staging 0.83.0 and CWSDPMI under `/opt/dos-toolchain`. It has no Node and no `wasm-bindgen`, so the parity job installs the pinned CLI. Changes to tool versions belong in the image repository, followed by a new digest here.

For local runs, `vendor/{djgpp,dosbox,cwsdpmi}` holds the same layout. The directory is git-ignored and never committed. `tools/setup-dos.sh` links `vendor` to `$DOS_TOOLCHAIN` when `vendor/djgpp` is absent, and does nothing when it is present:

```bash
DOS_TOOLCHAIN=/path/to/toolchain tools/setup-dos.sh
```

Only the DJGPP stub and CWSDPMI are used at run time; they are data, not a compiler. Do not install system packages to make a build pass.

## Performance

`FIZZ2.EXE /BENCH` and `cargo run --release -p fizz-ep2 --example bench` measure what the slice costs per tick. The budget is one tick at 60 Hz, 16,667 us, shared by the simulation step, the drawing and the copy to the screen.

### How `/BENCH` measures

The run plays the slice script once from a fresh level (1,757 ticks), unpaced, and times three sections of every tick: the step (`fizz_ep2::step`), the drawing (`render_slice`: the picture from `draw_slice` into the 320 by 200 buffer plus the HUD box) and the copy of the buffer to video memory (`present`). It prints their average and largest cost in microseconds, a total, and the final state hash, which must equal the golden's (`BENCH HASH`), so a bench run also proves the world it timed was the slice. It also prints a `BENCH FRAME <tick> <digest>` line for each of eleven ticks: an FNV-1a digest of the whole 320 by 200 frame, HUD box included, taken outside the timed sections, which `tools/check-dos.sh` compares with the digests the host computes from the same shared routines (`cargo run -p fizz-present-dos --example frames`), so a drawing routine that exists only in the DOS build is proved to draw the same pixels. It then prints `EXIT`, `FPU CW` and `VECTORS RESTORED` like the other modes. `FIZZ2.EXE /BENCH 120` times only the first 120 ticks (about a second at the settings below) for quick measurements while changing the drawing; a limited run ends on an earlier hash and is for timing only.

A 486 has no `rdtsc`, so the stopwatch is PIT channel 0, which the 60 Hz interrupt already programs: `timer::clocks()` is the interrupt count times the divisor (19,886) plus how far the counter has counted down in the current period, read with the latch command. One count is 0.838 us (1,193,182 Hz). That is fine enough for sections of tens of microseconds or more, and each section is timed per tick rather than in a loop, so the maxima are real. A reading costs two port reads and a port write, about 5 counts (4 us) in DOSBox at 26,800 cycles; `/BENCH` measures that first (`reading cost` on the `BENCH TIMER` line) and subtracts it from each section. Two edge cases are handled: an interrupt between the counter read and the interrupt count (the pair is read again), and the counter having reloaded before IRQ 0 has run, which makes a reading one period low (the stopwatch adds a period when a reading goes backwards). The 60 Hz handler itself still runs during the bench and appears in the maxima. Interrupts, vectors and pacing are unchanged, and the vectors are restored on exit and on panic like the other modes.

### DOSBox settings

`tools/check-dos.sh` runs the bench with `core=normal` and `cpu_cycles = 26800`, about a 486DX2-66 (26.8 million cycles a second), through `DOS_CYCLES=26800 tools/dosrun.sh`. The setting is the plain number: DOSBox Staging 0.83 rejects the form `fixed 26800`, logs `CPU: Invalid 'cpu_cycles' setting: 'fixed 26800', using '3000'` and carries on at 3,000 cycles a millisecond. `tools/dosrun.sh` now exits with status 125 and prints that log line whenever DOSBox reports an `Invalid '` setting, and `tools/check-dos.sh` tests the guard with the rejected form. Other modes keep `cpu_cycles = max`. The whole script takes about five seconds to emulate at 26,800 cycles, so the bench timeout is 120 seconds.

`/BENCH` then times one busy picture (tick 1190, in the snack nook) 120 times with no captions and 120 times with all six caption slots full (`EventCaptions::show_six`), and prints the `BENCH CAPTIONS` lines; the same pass runs with effects playing over the music under `/BENCH /AUDIO`. Six captions cost about 3.2 ms a picture in DOSBox at 26,800 cycles a millisecond (3.8 ms before `draw_text` looked each glyph up once); the figures and what is DOSBox-only are in [`DOS-CHECK.md`](DOS-CHECK.md#bench-six-captions-and-effects).

`/BENCH` also times a loop of 200,000 `dec`/`jnz` pairs (400,000 instructions, in 100 chunks, with the same stopwatch) and prints it as `BENCH CALIBRATE <loops> loops in <us> us (2 instructions per loop)`. DOSBox's normal core charges one cycle to each simple instruction, so the instructions per millisecond, `2 * loops * 1000 / us`, equal the configured cycles per millisecond. Measured: 2,968 at a setting of 3,000, 11,987 at 12,000, 26,739 at 26,800 and 80,128 at 80,000 (within 1% each time). `tools/check-dos.sh` asserts the implied rate is within 10% of the configured cycles, so a run that did not get the speed it asked for fails. The check also asserts the line shapes, the hash, the seven frame digests against the host's, the platform lines, positive averages for every section and a step average under 16,667 us, and prints the figures. It sets no tight bound on any of the timings.

### Drawing changes

Each change was measured with `FIZZ2.EXE /BENCH 120` (the first 120 ticks) at 26,800 cycles a millisecond and kept only for a clear gain. The figures are the drawing average in microseconds; the step did not move, and the copy moved only where stated.

| Change | Drawing before | Drawing after |
| --- | --- | --- |

| `memcpy` on `rep movsd` in the same file (the copy to video memory ends in it; the copy went from 3,589 to 599) | 11,434 | 11,429 |

Tried and not kept, because the gain was a few percent at most: a generic parameter in place of the `&mut dyn FnMut` for the tile colours (under 1%), and drawing glyphs four pixels at a time through a nibble mask (2.7%, for more code than the gain is worth).

What stayed identical: the pinned frame digests in `fizz-slice-view` (ticks 0, 150, 270, 400, 602, 700, 865, 1000 and 1268), every `fizz-view` test, the replay golden, the state hash (`PARITY ok 2145503c0d3b625f` at the time; look and aim have since moved it to `0edebb797e63edff`) and the seven DOS frame digests. The simulation, `fizz-phys` and `fizz-ep2` were not touched. The portable changes (the tile layer, the sprite blit, the door list) are in the code the Web build also runs; each has a test against the older definition of the picture, and the Web build was not timed.

How the drawing's last 2,800 us splits (first 120 ticks): the figures come from leaving pieces out, measured at 3,000 cycles before the setting was corrected and scaled to this one, so they are approximate. The sky and tile layer is about 600 us (writing the 64,000 bytes once is about 600 us on its own; the rest is the per-tile colour lookups and the run bookkeeping), the HUD text about 530 us, the sprites and the key, chicken and shots after the tiles about 575 us, and the camera and the black HUD strip the remainder.

The Two-Row Stack HUD (the score, the key tray and the wider box) was measured on the whole script at the same settings, taking the drawing from 2,952 us on average (largest 8,007) and 3,682 us in all (largest 8,776) to 3,180 us (largest 11,781) and 3,920 us (largest 12,546), with the step 131 to 140 us (the HUD's animation is fed there). That is 1.08 times the drawing and 1.06 times the tick, well inside the roughly 1.7 times the design counted for the box's own word operations (810 against 486 a frame) because the box is a small part of the drawing. The largest tick grows by 3.8 ms because a tick that renders the strip again (a pickup's ring, each step of the score counting up) pays for rendering 3,240 pixels and the glyphs on top of the copy; it stays at 75 percent of the 16,667 us budget at 26,800 cycles a millisecond. The state hash is the golden's `e3d629fda94149ab` throughout.

### The cost unit in DOSBox

The calibration loop (see above) shows what a unit of cost is: one cycle for a simple instruction, so at 26,800 cycles a millisecond a simple instruction costs 37 ns. The `rep stosd` and `rep movsd` of a 64,000-byte frame (16,000 dwords) take about 600 us, one cycle a dword, as the `BENCH PRESENT` figure of 599 us shows. The cost of the drawing is the number of instructions and string-instruction elements it runs. That is why the fixes that mattered run fewer of them (one long `rep` for many short loops, one clip for many, one table read for a `match`).

It is also a caution: a count of one cycle an instruction is not a 486's. Many simple instructions take one clock there, but loads, stores, branches and string instructions take more, so the absolute figures are a guide to the order of magnitude, and they say nothing about the x87.

### What the numbers say

The step is cheap: about 2,800 emulated cycles a tick (103 us at 26,800), 0.6% of the budget. The drawing was the problem: 107% of the budget on its own at 26,800 cycles and 239% at 12,000, so the slice did not hold 60 Hz at either setting. After the changes above the drawing is 2,728 us (16% of a tick) at 26,800 and 6,105 us (37%) at 12,000, and a whole tick costs 21% and 46% of the budget, the largest tick 23% and 52%. In the emulator, then, the slice holds 60 Hz at both settings with room to spare. The target of the drawing under 30% of a tick is met at 26,800 cycles and missed at 12,000.

Writing the 64,000-byte frame once costs about 600 us and copying it to the screen the same again, so a full-frame redraw plus the copy is about 7% of a tick before any tile, sprite or text is drawn. What remains is small pieces (glyphs 2.7%, looking sprites up once instead of by string compare, not drawing the rows under the black HUD strip, formatting the HUD numbers without `core::fmt`), each a few percent, and a change of design (keeping the scene between ticks and drawing again only what moved) that these figures do not call for.

The copy figure is DOSBox's cost for 16,000 dword writes to its emulated video memory and does not stand for a real card: a real VGA's bus speed decides it, and a real ISA or PCI card takes several milliseconds for 64,000 bytes whatever the instruction. Treat it as a lower-confidence figure than the other two; a slow ISA card alone could take a large share of the budget.

The figures were taken before look and aim and the machine probes were added, and have not been taken again. The cluck captions came after them and were checked at the same settings (the drawing stayed near 2,740 us a tick), but the tables were not redone. `tools/check-dos.sh` still runs `/BENCH` at 26,800 cycles and holds the loose bounds above; the tables here are the measurement of `FIZZ2.EXE` at 69,632 bytes, which is 88,064 bytes now.

These numbers do not say how a real 486DX behaves. DOSBox cycles are an approximation: it does not model cache, memory or bus timing, or a slow ISA video card, and the cost of x87 instructions, which the step uses for every `f64` operation and the drawing uses for each sprite position (`tile_px` takes a floor through `f64`), is not measured. DOSBox charges them the same as other instructions, so the step and the position arithmetic are floors, not estimates. The mapping from a cycle count to a named 486 model is a guess. No i486 cycle weighting of the instruction stream (as Fizz 1's `cyc486.py` does) was run for these changes, and `valgrind` is not installed here, so there is no instruction count either. That the changes help a real 486 rests on their running fewer instructions (a `rep stosd` stores a dword in about a clock after a few clocks of start-up, against five or more instructions for the generic loop), not on a measurement. The 486 floor claim stands on the order of magnitude until the build is run on hardware or a cycle-accurate model.

## Size budget

A 1.44 MB floppy holds 1,474,560 bytes raw, about 1,457,664 bytes of data area. Fizz 1's release scripts set the reserves:

| Disk | Room for the EXE and data | Reserve |
| --- | --- | --- |
| FreeDOS-bootable | About 1.17 MB | FreeDOS needs about 153 KB and 64 KB is kept free for saves |
| Plain | About 1.39 MB | 8 KB kept free |

The budget covers the executable and the Fizz Asset Packs (`.FAP`) together (see [Assets and packs](ARCHITECTURE.md#assets-and-packs) and [`FAP.md`](FAP.md#packaging-on-a-fizz-1-floppy) for the planned format and floppy rules). `tools/check-dos.sh` prints `SIZE <bytes>` for `FIZZ2.EXE` against a provisional `BUDGET 1100000` and fails if it is over; it counts the executable alone until packs exist, and then counts both. The figure is a tracked metric, not a design limit. Fizz 2's own save and config reserve is still to be confirmed. `FIZZ2.EXE` is 111,104 bytes, unstripped (with look and aim, the captions, the probes, the check screen, DOS sound, the help screen and positional sound), about 10.1% of the budget. At Milestone 0 it was 32,768 bytes; with the slice (the rules, the level, the sprite data and the drawing) it was 72,192 bytes, and deleting the marker's rules, drawing and replay took it to 61,440 bytes, about 5.6% of the budget. The `/BENCH` mode adds about 3.6 KB (62,976 to 66,560 bytes), and the drawing changes with the frame digests add about 3 KB more (69,632 bytes). The probes, `/PROBE` and the check-screen builder it links add about 13.8 KB (70,656 to 84,480 bytes). `FIZZ2.EXE` with the DOS music service and the lower-case caption font is 154,112 bytes, about 14.0% of the budget; the two register streams are 31,984 bytes of it (11,844 for OPL2 and 20,140 for OPL3), and the stepper, the service, `/MUSICTEST` and `/BENCH /AUDIO` the rest. With the eleven sound effects after the cluck (7,872 bytes of OPL records and 988 of speaker divisors for all fifteen, 6,360 more than the cluck alone), every event wired to its effect and the six-caption bench, `FIZZ2.EXE` is 201,216 bytes, about 18.3% of the budget; it was 190,976 bytes before the effects.

For scale, Fizz 1 embeds about 436 KB of assets in an 862 KB stripped executable: `sprites.bin` 102,252 bytes, `sound.bin` 279,348 bytes and `titles.bin` 54,488 bytes. The Episode 2 sprite design canvas holds 211 sprites, about 146 KB at one byte per pixel and about 73 KB at four bits per pixel. That count includes variants of Ben and three enemy rosters, so the sprites that ship will be fewer. Music and the larger backdrops are likely to take more room than sprites do.

## Not verified

- Real 486 hardware. Every DOS result comes from DOSBox.
- The hardware probes on real machines: see [`DOS-CHECK.md`](DOS-CHECK.md#not-verified) for the base+2 read on an OPL3, OPL4, ESS and Yamaha clones, the FM of an AWE or ViBRA, a monochrome VGA and a machine with no x87 (forced values only).
- x87 cycle cost. DOSBox with `cycles=max` hides it, and a fixed cycle count charges every simple instruction alike; the `/BENCH` figures are DOSBox's, not a 486's (see [Performance](#performance)).
- The live Web keyboard and canvas on a real browser session. The WASM module is replayed under Node and Bun, and headless Chromium has received key events for both layouts over the DevTools protocol, but a person has not played it.

## Safe writes and INT 24h

`FIZZ2.CFG` is replaced, never truncated in place (`dos/fizz2/src/cfgfile.rs`, called by `sound::save`). A save writes `FIZZ2.NEW`, closes it, reads it back and compares the bytes, deletes `FIZZ2.CFG` (a missing file is fine) and renames `FIZZ2.NEW` to `FIZZ2.CFG` (`dos::rename`, INT 21h AH=56h). Power lost before the delete leaves the old file; between the delete and the rename leaves only `FIZZ2.NEW`, and `sound::load_file` reads `FIZZ2.NEW` when `FIZZ2.CFG` is missing (the next save then replaces it). If a step fails while the old file is still there, the new file is deleted and the old one is untouched; the error returns to the caller, which is how the Options screen says "Could not write FIZZ2.CFG". Reading never writes: flags and recovery leave the disk alone.

While saving, `dos::FailCritical` answers a DOS critical error with "Fail", so a write-protected floppy or an open drive door returns an error code from the call instead of DOS printing "Abort, Retry, Fail?" over mode 13h. The handler is three real-mode bytes (`mov al,3; iret`) written into one paragraph of conventional memory from DPMI 0100h and installed with DPMI 0201h on the real-mode INT 24h vector; dropping the guard puts the old vector back and frees the paragraph. It registers on the clean-up list too, so an exit or panic during a save restores the vector like every other one. If DPMI refuses the allocation the save runs unprotected. A read-only `FIZZ2.CFG` fails at the delete (error 5) and is covered by `tools/check-dos.sh`; whether a truly write-protected floppy raises INT 24h through DOSBox's emulated drives, or through a real BIOS, is not something the headless run can show.
